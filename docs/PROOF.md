# Project write-ups, with numbers and limits

The long form of the four project cards on the [profile](../README.md). Each entry says what the project does, what was caught and fixed, and where its numbers stop being reliable.

## LinkedIn Engagement Manager (LEM)

**At stake if money rode on it:** the live app on an old release for a day with nobody told. Version v0.176.5 stayed live while v0.177.0 to v0.178.1 were tagged, and the only trace was a warning inside a green run. **What I did:** a classifier ships a release on its own only when every database change matches a safe additive shape, and holds anything it cannot parse. A hold opens one issue with the exact deploy command and emails me, and an hourly check alerts when the oldest missing release is more than 3 hours old. Across all 134 past migrations, 102 would have shipped on their own and 32 would have held, each with a named reason ([#2194](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/pull/2194), 68 classifier tests). The alert has fired in production and the issues closed themselves once production caught up ([#2392](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/issues/2392), [#2414](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/issues/2414)); holds clear when a person runs the deploy: [#2268](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/issues/2268) cleared in about nine hours and #2392 in about two days. The 134-migration count is as of that pull request.

Keeping up a LinkedIn presence means a content plan, posts at the right hours, and replies and comments every day. [LEM](https://github.com/christopherqueenconsulting/linkedin_engagement_manager) is a web app (FastAPI, Celery and Redis, MySQL, React, Selenium, LiteLLM, Docker Compose) that builds a 30-day content plan, runs AI-generated posts through quality gates and an optional approval step, and handles engagement under per-user targeting and daily caps. It is live at [lem.christopherqueenconsulting.com](https://lem.christopherqueenconsulting.com/).

In more detail: in September 2026 the live app sat on v0.176.5 for about a day while v0.177.0 to v0.178.1 were tagged, and the only trace was a warning inside a green run. Since 2026-09-25 an [hourly check](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/blob/main/.github/workflows/deploy-drift-check.yml) compares the live app's public version with the published releases and opens one issue when a release has waited too long ([#2194](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/pull/2194)).

Limits: deployed and CI-gated (continuous integration: tests run on every change); no revenue.

## CPCC Task Automation (instructor admin tool)

**At stake if money rode on it:** one false "does not compile" verdict floored a submission's whole grade. **What I did:** a real compiler (`g++ -fsyntax-only` for C++, `javac` for Java, Python's `compile()`) now decides compile errors before scoring. If no compiler is available or the run times out, the gate says "cannot verify" and the model's judgment stands, so a missing toolchain never fails a student. The compile gate only compiles student code (a separate, off-by-default, sandboxed output check can run programs), and every override is logged ([#267](https://github.com/christopherqueenconsulting/cpcc_task_automation/pull/267), [compiler-gate.md](https://github.com/christopherqueenconsulting/cpcc_task_automation/blob/master/docs/compiler-gate.md)). Write-back is scoped: assignment grades are saved as drafts and the tool never clicks Publish (an opt-in setting, off by default, can update grades already published), but the quiz page has no draft state, so a quiz write-back posts to the student at once, which is why dry run is the default.

Every week, for each course I teach, I took attendance, recorded withdrawals and graded programming work by hand, and one missed submission is a wrong record. [CPCC Task Automation](https://github.com/christopherqueenconsulting/cpcc_task_automation) (Python, Streamlit, Selenium, LangChain, OpenRouter) drives the student information system and the learning platform through a real browser, grades against a rubric, and writes grades back as drafts where the platform allows one (it never clicks Publish, so the instructor publishes). The withdrawals sync and the grade write-back default to a dry run; attendance is written directly to the student information system. The live BrightSpace fill-and-save flow is marked unverified in the repo's `brightspace_writeback.py`.

In more detail: the model flagged valid C++ as "does not compile", a major rubric error, and took the whole grade to the floor. I chose a compiler because a deterministic check fits a compile verdict better than prompt tuning; I did not record whether prompt changes were tried first, or how the false verdict was found. A [real compiler now decides "does not compile"](https://github.com/christopherqueenconsulting/cpcc_task_automation/blob/master/docs/compiler-gate.md), and the compile check never runs student code (merged 2026-09-02, [#267](https://github.com/christopherqueenconsulting/cpcc_task_automation/pull/267)). When the compiler cannot run (a missing toolchain, a timeout) the gate treats that as "cannot verify", not "does not compile", and the model's judgment stands. The repo's design note records one false positive that floored a whole grade; I did not measure how often the model made that mistake, so there is no rate.

Limits: invite-only, built for instructor admin work; no public demo; I am its only user, for my own courses ([case study](https://christopherqueenconsulting.com/work/cpcc-task-automation/?utm_source=github&utm_medium=readme&utm_campaign=cpcc-task-automation)).

## hearing-copilot: speaker identification

**At stake if money rode on it:** a wrong speaker name pins words on the wrong person. **What I did:** I scored the model on 91 minutes of real court audio, with Oyez's speaker-aligned transcripts as ground truth, before trusting it, and set the confidence threshold (0.65) from that table, so only confident names are accepted automatically and the rest stay suggestions or "unknown". Early uncalibrated runs showed 44% wrong names; the cause was the embedding model returning unreliable scores for some clip lengths, fixed with a fixed 6-second window, which also made it faster ([RESULTS.md](https://github.com/gitchrisqueen/hearing-copilot/blob/main/eval/diarization/RESULTS.md)). The limits below still apply: one hearing, no train and test split, no confidence interval.

A live transcript is only useful if it says who is talking. [hearing-copilot](https://github.com/gitchrisqueen/hearing-copilot) is a local JavaScript app that transcribes a hearing and labels the speakers. Before speaker identification went into the app, I ran an offline bake-off on real Supreme Court oral-argument audio, with Oyez transcripts as ground truth.

The number ([RESULTS.md](https://github.com/gitchrisqueen/hearing-copilot/blob/main/eval/diarization/RESULTS.md), dated 2026-07-24): in the cold-start run (no voice samples enrolled beforehand) on *Bowe v. United States* (argued 2025-10-14, 91 minutes, 12 speakers), it auto-accepted 89.8% of the chunks (short audio segments) and was right on 99.2% of the chunks it auto-accepted.

Limits: this is one hearing and one cold-start run, clustered and scored on the same 91 minutes with no train and test split, and RESULTS.md gives no chunk counts or confidence interval for the two percentages. The accept threshold (0.65) was chosen from a calibration table over both main runs, so the headline is not held-out; that table lists 91 to 92% coverage at 0.65, a little above the 89.8% headline, and I have not re-derived which threshold produced the headline row. The cold-start numbers use an optimistic greedy cluster-to-speaker mapping; no Zoom-quality audio has been tested; the cold-start chunk total is not reported.

## panthera and lottery-guru: paper trading and a chance experiment

**At stake if money rode on it:** scheduled runs produced no picks for 14 slate days (145 passes) while every run showed green and the data stayed current. **What I did:** I replaced the config whitelist that excluded the postseason with one function that decides what is in scope ([fix 1c4619f](https://github.com/gitchrisqueen/panthera/commit/1c4619f), [#65](https://github.com/gitchrisqueen/panthera/pull/65)), and added a daily health check of nine checks ([#66](https://github.com/gitchrisqueen/panthera/pull/66)) whose silence threshold was measured on 73 slate days: 14 hits and no false positives before the outage (in-sample). It flags a no-picks slate the next morning, about 26 hours at the earliest, which the workflow states as an accepted cost, and other faults can take longer; a data-staleness fault ([#81](https://github.com/gitchrisqueen/panthera/issues/81)) took about 5 days to surface because bot pushes had been failing since 2026-10-23 ([#83](https://github.com/gitchrisqueen/panthera/pull/83)). I also report the one supported strategy's +7.99% over 227 graded picks with its standard error, about 1.2 standard errors from zero, instead of calling it an edge. These are paper trades, not tips.

[panthera](https://github.com/gitchrisqueen/panthera) is an automated MLB paper-trading pipeline on GitHub Actions: odds snapshots three times a day, picks from documented rules, graded the next morning, ledger committed to git. Each strategy is pre-registered, meaning its success criteria are declared in its YAML file in the repo (self-declared in git, not independently timestamped, and I have not checked that each file's first commit predates the first graded pick), and [the report](https://github.com/gitchrisqueen/panthera/blob/main/reports/BETTING_REPORT.md) says plainly that at these sample sizes no ROI bar controls both error rates. [lottery-guru](https://github.com/gitchrisqueen/lottery-guru) is a null-hypothesis experiment on lottery-draw prediction: daily predictions from folk strategies plus LLM arms, scored against real draws, with z and p per strategy on [a leaderboard](https://github.com/gitchrisqueen/lottery-guru/blob/main/REPORT.md).

In more detail: the repo's own [health-check workflow](https://github.com/gitchrisqueen/panthera/blob/main/.github/workflows/health.yml) records where it came from: the last regular-season pick landed on 2026-09-27, the first all-silent slate was 2026-09-29, and, by the repo's own count, nobody noticed for 14 slate days because every workflow stayed green. The cause was a config whitelist that excluded the MLB postseason, [fixed on 2026-10-15](https://github.com/gitchrisqueen/panthera/commit/1c4619f); the report's later picks, such as 2026-10-19, are postseason ones. A daily health check now scores each finished slate day and opens an issue for a dead one; its run status alone does not show a dead slate.

Limits: panthera is paper trading only, and its ledger is idle outside the MLB season. On the ledger updated 2026-10-23, the one strategy marked supported shows +7.99% ROI over 227 graded picks (124 wins, 103 losses). The 6.7 points in the report is one standard error, not a confidence interval, so +7.99% is about 1.2 standard errors above zero: not distinguishable from no edge. "Supported" is the repo's own label for a screen-grade verdict, not a finding. Its regular-season picks returned +8.59% and its 4 postseason picks -36.90% (too few to read), it overlaps 54% with other strategies' picks, and with several strategies running at once the report expects at least one false-positive screen, so it treats the result as a screen, not proof. lottery-guru's expected result is that every arm converges to chance, and its leaderboard applies no multiple-comparison correction across its many strategies.

Also: [CueSyncAR](https://github.com/gitchrisqueen/CueSyncAR), an iOS augmented-reality billiards prototype in Swift, declared paused on 2026-09-10 in its own README.

## cqc, the tool behind the terminal

[cqc](https://github.com/gitchrisqueen/cqc) is a small command line tool whose six checks are also MCP tools. `cqc mcp connect skills` starts its MCP server and lists them, and `cqc call <tool>` runs one. Each tool is based on work above:

| Name | What it does | Where the idea comes from |
| --- | --- | --- |
| `llm_audit` | `--sample` prints the sample scorecard (five areas, A to F); `--logs` grades reliability and spend efficiency from real call logs. | [The audit](https://christopherqueenconsulting.com/ai-ops-audit/) |
| `real_check` | Decides whether source code compiles by asking a real compiler; it never runs the code. | [compiler-gate.md](https://github.com/christopherqueenconsulting/cpcc_task_automation/blob/master/docs/compiler-gate.md) |
| `drift_watch` | Compares a live version with the latest GitHub releases. | [deploy-drift-check.yml](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/blob/main/.github/workflows/deploy-drift-check.yml) |
| `browser_flow` | Plans browser steps as a dry run. | [CPCC Task Automation](https://github.com/christopherqueenconsulting/cpcc_task_automation) |
| `ci_pipeline` | Checks GitHub Actions workflows for unpinned actions and other fail-open settings. | [ci.yml in this repo](https://github.com/gitchrisqueen/gitchrisqueen/blob/main/.github/workflows/ci.yml) |
| `human_gate` | Holds a draft until a person approves it. | [CPCC Task Automation](https://github.com/christopherqueenconsulting/cpcc_task_automation) |
